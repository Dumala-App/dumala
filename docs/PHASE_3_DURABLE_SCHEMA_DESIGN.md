# Phase 3 Durable Schema Design

Updated: 2026-06-25

Status: Accepted design baseline before Supabase provisioning

Related ADR: `docs/ADR_PHASE_3_CLOUD_PLATFORM.md`

## 1. Purpose

This document defines the first durable PostgreSQL schema shape for Phase 3 cloud accounts and synchronization. It turns the platform decision into a reviewable data model before any Supabase project, migration, or production cloud data is created.

The design preserves Dumala's local-first behavior while preparing for:

- secure user accounts
- one owner-controlled club workspace in Phase 3
- future club memberships and roles in Phase 4
- non-destructive local-to-cloud migration
- offline mutation replay
- cross-device synchronization
- visible conflict handling
- export, deletion, monitoring, and audit logging

## 2. Scope

Included in this schema baseline:

- account profile metadata
- clubs
- club memberships
- devices
- sync cursors and mutation idempotency
- core club domain records
- assessment reproducibility metadata
- payment ledger records
- lifecycle audit events
- soft deletion and tombstones
- RLS-ready tenant ownership columns

Deferred from Phase 3:

- invitation UI
- full multi-user collaboration behavior
- simultaneous editing UX beyond conflict detection
- public player, staff, or club profiles
- public media hosting
- multiple squads per club
- online payment processing
- official accounting or invoice compliance

## 3. Naming and Common Columns

Use snake_case table and column names in PostgreSQL. Use stable UUID primary keys for all durable records.

Every tenant-owned synchronized table should normally include:

| Column | Type | Requirement |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by client for offline-created records |
| `club_id` | `uuid` | Required foreign key to `clubs.id` |
| `created_at` | `timestamptz` | Required, set by database where possible |
| `created_by` | `uuid` | References authenticated user when available |
| `updated_at` | `timestamptz` | Required, set by database where possible |
| `updated_by` | `uuid` | References authenticated user when available |
| `version` | `bigint` | Required optimistic-concurrency version, starts at `1` |
| `deleted_at` | `timestamptz` | Soft-delete tombstone timestamp |
| `client_created_at` | `timestamptz` | Optional diagnostic device timestamp |
| `origin_device_id` | `uuid` | Optional reference to the device that created the record |

Rules:

1. Client-generated UUIDs are required for offline-created records.
2. `club_id` is mandatory for every private club record.
3. Display names, array indexes, and roster numbers are never durable identities.
4. Use soft deletion where deletions must synchronize across devices.
5. Use database timestamps as authoritative sync metadata.
6. Keep device timestamps as diagnostics only.
7. Use JSONB only for bounded, versioned structures that do not benefit from relational querying.

### `user_profiles`

Private account profile metadata. Authentication secrets remain in Supabase Auth and are not copied here.

| Column | Type | Notes |
| --- | --- | --- |

| `account_state` | enum | Defaults to `active` |
| `accepted_terms_version` | `text` | Required before cloud migration |
| `accepted_privacy_version` | `text` | Required before cloud migration |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |
| `pending_deletion_at` | `timestamptz` | Optional |

- `display_name` must not be treated as unique identity.
- `deleted_at` requires `account_state = 'deleted'`.

### `club_memberships`

Membership and future role foundation. Phase 3 creates an owner membership automatically; Phase 4 expands invitations and role behavior.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `club_id` | `uuid` | References `clubs.id` |
| `user_id` | `uuid` | References authenticated user |

User-controlled installation records for sync diagnostics and revocation. Do not collect hardware identifiers or advertising identifiers.

| Column | Type | Notes |

## 6. Sync and Migration Tables

### `workspace_imports`

Tracks explicit local-to-cloud migrations.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `club_id` | `uuid` | References `clubs.id` |
| `user_id` | `uuid` | Importing user |
| `device_id` | `uuid` | Origin device |
| `source_backup_version` | `text` | Example: Full Workspace V3 or V4 |
| `manifest_hash` | `text` | Idempotency and verification fingerprint |
| `record_counts` | `jsonb` | Bounded counts by entity type |
| `status` | `text` | `started`, `completed`, `failed`, `rolled_back` |
| `started_at` | `timestamptz` | Required |
| `completed_at` | `timestamptz` | Optional |
| `failed_at` | `timestamptz` | Optional |
| `failure_code` | `text` | Optional stable error code |

Constraints:

- Unique `(club_id, manifest_hash)`.
- Replaying the same completed import must not duplicate domain records.

### `sync_mutations`

Server-side idempotency ledger for client outbox replay.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `club_id` | `uuid` | References `clubs.id` |
| `user_id` | `uuid` | Authenticated sender |
| `device_id` | `uuid` | Sending device |
| `idempotency_key` | `text` | Stable client mutation key |
| `entity_table` | `text` | Target table name |
| `entity_id` | `uuid` | Target record ID |
| `operation` | `text` | `insert`, `update`, `delete`, `function` |
| `base_version` | `bigint` | Client-known version before mutation |
| `result_version` | `bigint` | Version after successful mutation |
| `status` | `text` | `applied`, `rejected`, `conflict`, `duplicate` |
| `error_code` | `text` | Optional stable error code |
| `created_at` | `timestamptz` | Required |
| `applied_at` | `timestamptz` | Optional |

Constraints:

- Unique `(club_id, device_id, idempotency_key)`.
- A stale `base_version` must return a conflict instead of overwriting current data.

### `sync_changes`

Append-only club change feed for pull synchronization.

| Column | Type | Notes |
| --- | --- | --- |
| `sequence_id` | `bigserial` | Primary ordered cursor |
| `club_id` | `uuid` | References `clubs.id` |
| `entity_table` | `text` | Changed table |
| `entity_id` | `uuid` | Changed record |
| `operation` | `text` | `insert`, `update`, `delete` |
| `record_version` | `bigint` | Entity version after change |
| `changed_by` | `uuid` | Authenticated user |
| `origin_device_id` | `uuid` | Optional |
| `changed_at` | `timestamptz` | Required |

Constraints:

- Index `(club_id, sequence_id)`.
- Pull cursors are based on `sequence_id`, not client clocks.

## 11. RLS Policy Shape

Default posture:

1. Unauthenticated users cannot read or write private tables.
2. Authenticated users can read and write only records whose `club_id` belongs to an active membership.
3. Phase 3 owners can read and write their own club records.
4. Removed or suspended memberships lose access immediately.
5. Service-role access is restricted to trusted server-side jobs and must never appear in browser code.

Policy helper concept:

```sql
exists (
  select 1
  from club_memberships m
  where m.club_id = target_table.club_id
    and m.user_id = auth.uid()
    and m.membership_state = 'active'
)
```

Additional RLS checks:

- Inserts must require the target `club_id` to be a club where the user has active membership.
- Updates must prevent changing `club_id`.
- Soft deletes follow the same write rules as updates.
- Database functions must verify membership internally and not rely only on function callers.

## 12. Required Indexes

Minimum index families:

- every foreign key
- `(club_id, deleted_at)` on tenant-owned tables
- `(club_id, updated_at)` where pull queries need chronological filtering
- `(club_id, sequence_id)` on `sync_changes`
- `(club_id, device_id, idempotency_key)` on `sync_mutations`
- `(club_id, user_id)` on `club_memberships`
- `(user_id, revoked_at)` on `devices`
- entity-specific indexes for common views, such as `(club_id, player_id)` on assessments and payment entries

Indexes should be revisited after repository queries are implemented.

## 14. Open Decisions Before Migrations

These decisions should be settled before SQL migration files are written:

1. Whether to implement enums as PostgreSQL enum types or check-constrained text.
2. Whether roster numbers must be unique per active club.
3. Whether tactics workspaces should support multiple saved boards in Phase 3 or remain one active board per club.
4. Which standings snapshots remain product-relevant after cloud migration.
5. Whether payment ledger records should be included in the first cloud migration if the local payments MVP is still incomplete.
6. The exact RLS test harness and database testing tool.
7. The retention period for deleted clubs, audit events, exports, and backups.

## 15. Next Task

The next Phase 3 task is to design the non-destructive local-to-cloud migration and rollback workflow against this schema baseline.

That workflow should specify:

- migration states
- pre-migration backup creation
- import manifest format
- per-entity transform rules
- idempotency keys
- verification counts and integrity checks
- failure recovery
- rollback behavior
- user-facing migration copy and diagnostics
